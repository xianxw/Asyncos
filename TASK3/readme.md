## 异步化改造思路

这份代码当前是一个典型的同步式 SD/MMC 驱动：上层通过 `SdMmc` 调用初始化、读块和写块接口，底层则直接通过寄存器轮询完成命令发送和数据搬运。

从代码职责上看，可以分成四层：

- `sdmmc.rs`：驱动主流程，负责初始化、发送命令、读写块，也是阻塞点最集中的地方。
- `cmd.rs`：把 SD 协议命令转换成控制器的 `Cmd` 位图，属于协议编码层。
- `regs.rs`：控制器寄存器定义和位图抽象，属于硬件抽象层。
- `utils.rs`：解析 CID、CSD 等响应数据，和同步或异步策略关系不大。

### 思路一：阻塞点异步化（轻量改造）

这个方案的目标不是改变硬件交互方式，而是把当前的忙等逻辑改成可挂起、可恢复的状态机。也就是说，仍然是同样的寄存器访问和 FIFO 读写，但等待过程不再一直占着线程。

当前最明显的阻塞点集中在这些地方：

- `sdmmc.rs` 里的 `wait_until`
- `send_cmd` 中等待命令可发送、响应返回、数据传输完成的逻辑
- `init` 中按 SD 协议顺序执行的等待过程
- 读写块函数中的 FIFO 轮询逻辑

这个阶段建议保留硬件协议相关代码，不去大改 `cmd.rs` 和 `regs.rs` 的结构。比较合适的做法是：

1. 把 `wait_until` 改成基于 `Future` 或 `poll_fn` 的等待辅助函数。
2. 把 `send_cmd` 拆成“发起命令”和“等待完成”两个阶段。
3. 把 `init` 拆成多个可恢复的初始化步骤，而不是一次性顺序跑完。
4. 把读写块函数拆成状态机：先启动传输，再在数据可读/可写时推进 FIFO。

这种改造完成后，驱动会变成“协作式异步”，但底层还是轮询硬件状态；它的优势是改动小、风险低、容易保留原有协议逻辑。

### 思路二：深度异步化改造（中断 + DMA）

如果希望更彻底地异步化，就不能只改 `sdmmc.rs` 的控制流，还要把“完成信号”真正接到硬件事件上。这个层级的重点是：任务在等待时不主动轮询，而是靠中断或 DMA 完成通知来唤醒。

通常需要补进去的机制有：

- 中断唤醒：命令完成、数据传输完成、错误中断等事件触发后唤醒等待任务。
- 完成通知：把 raw interrupt status 和 masked interrupt status 统一纳入 async 任务的完成条件。
- DMA 传输路径：如果控制器和平台支持 DMA，读写块就可以从 FIFO 轮询升级为 DMA 驱动的数据搬运。

这个阶段一般会涉及以下代码变化：

- `sdmmc.rs`：从同步控制流改成完整的异步状态机，负责把命令阶段、数据阶段、收尾阶段串起来。
- `regs.rs`：增加或整理中断相关辅助方法，例如中断掩码配置、状态清除、完成条件判断、DMA 复位等。
- `cmd.rs`：大多数协议映射可以保留，但可以补充一些命令元数据，帮助状态机判断这条命令属于哪种异步流程。

这里有一个重要原则：`cmd.rs` 里最好仍然只负责“协议编码”，不要把 waker、poll、任务唤醒这类异步细节塞进去。异步调度逻辑应该放在驱动层，而不是命令描述层。

### 总结

如果只做轻量异步化，核心修改点在 `sdmmc.rs`，`cmd.rs` 和 `regs.rs` 基本可以保留。

如果做深度异步化，`cmd.rs` 可能只需要少量元数据调整，但 `regs.rs` 的中断/DMA 辅助能力和 `sdmmc.rs` 的状态机设计都需要一起升级。换句话说，真正的改造中心仍然是 `sdmmc.rs`，只是第三层级会把中断和 DMA 也纳入整体设计。
